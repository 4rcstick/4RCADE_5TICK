## 1. Working rules for this project

0. **Current workflow (since the Themes Manager move, 2026-10-22).** The user speaks first on planning, then suggestions are fitted around it. A big change goes to Claude Code as an md spec (decisions, a read-only STEP 1 audit, then STEP 2 implementation only after the user says "go", plus a test checklist), delivered as a real file; a small change gets a single Claude Code prompt. One pass at a time: the user tests and commits between passes and keeps the right to tweak after testing. Small hand edits can still be a plain "replace X with Y". Rules 1 to 4 below are the older hand-edit flow and apply only when the user is editing by hand.
1. After the user explains a change or bug, summarize in 1-2 sentences what will be done and which files need edits. The user then uploads the files requested.
2. Post zero code or syntax snippets until the user says they are ready. They say so when they agree with the suggested edits; otherwise they reply with questions or changes.
3. When ready: one code block per message. Wait for confirmation of placement (or questions) before the next block.
4. Code edits use "Replace X code, with Y code" in two separate code blocks.
   - **The user's stated preference (2026-10-18): a plain "replace X with Y"**, with the filename and any instructions written **above** the code block, never inside it. Text inside a block makes lines wrap and the edit hard to read. Always tag the block with a language (`xml`, `csharp`) so it keeps syntax colors and scrolls sideways instead of wrapping.
   - **Insertions are also "replace X with Y":** replace one unique existing line with that same line plus the new code. Do not give a separate "paste after this line" instruction.
   - **Anchors:** when X is not unique on its own, start it with the method signature (C#) or the nearest distinctive line or section comment (XAML), and say which lines are context only. Do not send a snippet that appears in more than one method without its signature. The closing bracket is a fine ending anchor.
   - **Whole functions:** when an edit replaces a whole function, the X block lists the entire old function. Nothing is implied or abbreviated.
   - **Never abbreviate a line to "..."** in a delete list; list the full text so the user can search for it.
5. If errors are expected during multi-file edits, say so in advance, name the window where they appear and where they clear.
6. Do not try to wrap up the session when the initial edits are complete. The user decides when to start a new session.
7. Planning conversations: let the user give their ideas first, then fit suggestions around them. Do not hand over a full plan before they have spoken.

### 1b. Lessons for writing edit instructions (learned on the Games List and cleanup passes; guidance, not rules)

- XAML has few helpful anchors. Give a distinctive search string (a label text, an x:Name, a handler name) and say which template or section the edit belongs to. Folder and game templates look almost identical, and two edits once landed in each other's template.
- For a large pure deletion in XAML, prefer a hand-delete with a start line and an end line; whitespace-only lines inside a block make find-and-replace miss.
- For deletions spread across a file (flat property removals), a list of single lines to search for works well. The user can eyeball red squiggles to confirm a clean build.
- **The user prefers a whole-file replacement for large or restructuring edits** (sent as a file download, or inline for a short file) over find-and-replace: no chance of deleting the wrong lines.
- Order a multi-edit change so build errors appear in one short window, and name that window up front. Remove readers before the properties they read (this pass removed the Basic tab, then the settings, then the view model, in an order that kept the build clean at the end).
- After a big restructure, Visual Studio can show stale generated-file errors (for example duplicate x:Name CS0229) that a clean and rebuild clears. Re-upload files after many edits so line numbers and text do not drift.
- Before sending an edit for a line, confirm the search text is unique in the latest uploaded file.
- Visual Studio can add a stray `using static System.Net.Mime.MediaTypeNames;` that makes `Application` ambiguous (CS0104); delete that line.
- A paste can truncate mid-element and give missing-closing-tag errors (XLS0305); a whole-file replacement avoids this.
- `d:DesignWidth` / `d:DesignHeight` on a UserControl are designer-only and do nothing at runtime. Size the real window in ThemeBuilderWindow.xaml.
- A Find in Files search for the removed names is faster than guessing which other files use them; the user can run it and upload hits.
- Claude Code can measure layout offscreen: a scratch harness that loads each tab at the real pane width (397, 395 for tab content, 385 with a scrollbar) found every clipped label in the 2026-10-22 layout sweep. Use it for any "text is cut off" pass instead of eyeballing.
- When a spec's drawing approach is in doubt, have Claude Code render it offscreen first (RenderTargetBitmap at 96, 120 and 144 DPI, counting line pixels); that caught the tiled grid brush's blurred and missing lines at 125% and 150% before any code was written (Background grid, 2026-10-23). But offscreen rendering is the software renderer: it did not reproduce the combined-geometry bug that only appeared on screen in the hardware path, so a clean offscreen result does not clear a drawing change; the on-screen test still decides.

- Build the Advanced tier of the Theme Builder layer by layer, starting with the **Games List** layer, and carry what is learned from each layer into the next. More small passes is accepted in exchange for refinement.

## 3. How the builder works today (verified in code)

### 3.1 Layout model
- Each theme can hold several **resolutions**. Each resolution has a layout: a list of layer entries with Id, X, Y, Width, Height, Z (draw order, higher on top), Visible, Name, ImagePath. Some entries also carry styling fields (Games List: section 5; shape, custom, Splash and Video Preview layers: section 3.8; Search & Buttons: section 3.10; Main Window Background: section 3.11; Game Info: section 3.12).
- **Every styling field is copied in one place:** `LayerLayoutEntry.CopyStyleFrom(source)` copies everything except Id, rect, Z, Visible, Name and ImagePath. CloneLayouts, the resolution-switch copy (preset path) and both Reset Layer branches call it, so a new style field only has to be added there (plus the registry defaults/fill-ins and the style key).
- Name is used by custom layers only. ImagePath is used by shape layers, custom layers, the Marquee logo, Random Game Display, the Main Window Background wallpaper, the Splash Image splash file and the Video Preview fallback image.
- A layer's placement therefore belongs to one resolution. Some layers have separate entries for two states (Random Game Display: "when a game is selected" and "when on the splash page").
- Presets in the combo box: 1280x720, 1600x900, 1920x1080, 1024x768, 800x600. Custom sizes are entered in the custom size row ("Custom..." in the combo), which has one button, **Apply** (`BtnAddCustomRes`, or Enter in either box): it switches to the typed size (a new size shows the New size layout prompt first, below) and commits it at once (`CommitPendingSize`), so it joins the combo and the row closes. The Keep button was removed 2026-10-28. A size is "pending" only when a Theme sizes button brings back a custom size that was removed but not saved; Apply, Save Adjustments or a theme save commits it, and switching away first discards it.
- **Removing a size (2026-10-26):** `BtnDeleteCustomRes` shows for any active size that has a layout in `Configuration.Layouts` (not for a pending size); it reads "Delete Size" on a custom size and "Remove Size" on a preset (`UpdateCustomResUi`). With only one size left (`CountRemovableSizes`, pending size not counted) it is disabled and its tooltip says why (`ToolTipService.ShowOnDisabled`). `BtnDeleteCustomRes_Click` asks for confirmation naming the size and the one shown next, removes that size from the working Layouts only, then switches to another size with a layout (`PickSizeAfterRemoval`: the theme's saved size when it still has a layout, else the remaining size nearest to the removed one) and rebuilds the combo and the Theme sizes row. A removed preset stays in the combo (picking it later starts a fresh copy of the layout being edited, like any new size); a removed custom size leaves the combo. It is an ordinary working edit: SavedThemeLayouts is not touched, so the size still shows on the Theme sizes row and in the hamburger's Layout size submenu until Save Changes writes the theme (whose layout list comes from Layouts), and closing the builder without saving restores it through the close-revert snapshot. Picking that size from the Theme sizes row before saving starts a fresh copy of the current layout (after the New size layout prompt, below), not the theme's saved one. Smart fullscreen reads SavedThemeLayouts (3.17), so a removed but unsaved size can still be picked there, shown from the theme's saved copy.
- A new resolution starts as a copy of the layout being edited (custom layers excluded, background resized to fit), including all styling values. **New size scaler (2026-10-28, decision 65, `new-size-scaler.md`):** before a size with no working layout is created, the "New size layout" prompt (`PromptForNewSizeScale`) offers A scale everything, B scale positions only, or C keep the layout as is (the 1:1 copy). It opens from three places, always **before** `RunSizePick`: a preset in the combo (`CboResolution_SelectionChanged` → `BeginNewSizePick`, which puts the combo back on the current size and opens the prompt through `Dispatcher.BeginInvoke` after the dropdown closes; OK reselects the size under `_loading` and runs the normal pick), a Theme sizes button for a size removed but not saved (`BtnSavedSize_Click`), and the custom size **Apply** button or Enter (`BtnAddCustomRes_Click`; the copy happens on Apply, which then commits the size). Cancel creates nothing: the combo stays on the current size ("Custom..." while a pending size is active, `RestoreResolutionComboSelection`), and on Apply the entry row and any pending size stay as they were. The choice reaches the copy through `_newSizeScaleChoice` (`RunNewSizeSwitch`), and `ScaleNewSizeCopy` runs `Services/LayoutScaler.Scale` on the new copy after the background resize and before `ResolveAndStoreFrom`, in both copy spots (`CboResolutionApply`, `SwitchToResolution`). Factors fx = newW / oldW, fy = newH / oldH, u = min(fx, fy), the old size being the layout copied from (a pending custom size when one is active). A: X / Y and Width / Height by fx / fy on every positionable layer, image layers and shape layers with a file included (final after testing at 1024x768: the layout fills the window and backdrops and frames stay aligned with their content; keeping each layer's ratio, the superseded first build, would leave the Marquee and Games List too small anyway), and FolderFontSize, GameFontSize, TextFontSize, SectionHeaderFontSize and BorderSize by u, clamped to the editor ranges (`MinTextFontSize` / `MaxTextFontSize` 6 to 72, `MinNavSize` / `MaxNavSize` for the two navs, the Random Game Display max sizes 6 to 200, `MinBorderSize` / `MaxBorderSize` 0 to 50); the Marquee entry's TextFontSize (the banner's 400x100 reference-box size) stays, its BorderSize (real pixels) scales. **On a mismatch** (the two factors differ as shown, `LayoutScaler.FactorsDiffer`, the warning-line test; 1366x768 from 720 matches) A only moves the Search & Buttons group (`LayerRegistry.IsPositionOnlyOnMismatch`): X / Y scale, Width, Height, TextFontSize and BorderSize stay. **The Video Preview keeps its shape on a mismatch** (third amendment 10, 2026-10-28): A scales its Width and Height both by u (`LayerRegistry.IsUniformSizeOnMismatch`, true only for `VideoPreview`), X / Y still by fx / fy (top-left at the scaled position), BorderSize by u as before, so it fits inside the area it would have covered stretched (720 to 1024x768: a 480x360 box becomes 384x288 at x0.8 / x1.067). Every other layer, the shape layers behind it and the Splash Image included, still stretches per axis. B: X / Y only. Radii, shadows, margins, nudges, colors, fonts, files, opacity, visibility, Z and names never change; the background is skipped (already resized); nulls stay null; everything rounds half away from zero. The prompt shows the sizes, the factors (`FormatFactor`, "0.0##") and, when `FactorsDiffer`, an aspect ratio warning. Preselection: the remembered `ConfigurationSettings.NewSizeScaleChoice` (settings.json, default "C"), or C when the ratio is far off (`LayoutScaler.IsFarOffRatio`, more than 15%); OK on a close ratio sets the remembered choice in memory only (Save Adjustments writes it), OK on a far-off ratio leaves it. The scaled layout is an ordinary working edit. **Persistence (confirmed in testing 2026-10-28):** Apply (and a preset pick) adds the size to the Resolution combo and makes it the working layout; the Theme sizes row reads the saved theme, so it changes only after Save Changes; Save Adjustments writes the working layouts to settings.json, so the size stays in the combo after closing and reopening the builder and after restarting the launcher; closing the builder without saving removes the new size (the close-revert snapshot), and picking it again shows the prompt again. Switching to a size that already has a layout, Remove / Delete Size, Load Theme and the hamburger Layout size pick never prompt. **Known limits** (parked in 6b): on a mismatch the Search & Buttons group can overlap when scaling down (at 1024x768 the search box partly covers the search label and the four buttons touch), because its positions shrink while its sizes stay; image layers (Splash Image, shape layers with a file) distort on a mismatch, since they stretch to the box; borders round half away from zero, so a 1px border stays 1px at x1.25 while a 2px border becomes 3px.
- The window sizes itself to the active resolution; the main window's LayoutCanvas is that size.

### 3.2 Layer registry (single source of truth)
Defined in LayerRegistry. Adding a layer = adding a definition. Defaults are authored at 1280x720 and scaled by width/height ratio for other sizes (starting points only; nothing scales at runtime).

Layers (registry order), with groups shown as one row in the Advanced list:
- MainBackground (not positionable, cannot hide; holds the main window wallpaper, see 3.11)
- **Shape Layer 01 to 04** (ShapeLayer01..04): background/border layers, see 3.8
- GamesList (cannot hide), MarqueePanel, SplashImage, VideoPreview
- Group **Game Info**: GameTitle, PublisherBlock, GameInfoNav, GameInfoBody, ImagePreviewsNav, ImagePreviewsBody
- Group **Search & Buttons**: SearchLabel, SearchBox, RandomButton, SortButton, OptionsButton, HamburgerButton
- Group **Random Game Display**: RandomGameDisplay, RandomGameDisplaySplash
- Footer
- Custom layers: Ids start with "Custom_", at most 10 per resolution, png/jpg/gif/APNG/mp4. They use the same box renderer and tabs as shape layers (3.8).

The old GamesListBg and MediaPanel layers are gone from the registry (their ID constants remain unused); Shape Layers 01 and 02 took over their default rects.

Group rules: parts of a group share one Z and appear as one row; the group edit page is built in code, one section per part. The "Hide this layer" checkbox is shown only for layers that can be hidden and are not box layers (shape and custom layers use a visibility dropdown instead).

### 3.3 Applying the layout to the main window
- MainWindow.ApplyLayout resolves the active layout and maps each Id to an element: sets Canvas Left/Top, Width, Height, Z, and Visibility. It runs at startup, on every ThemeBindingsRefreshed, and after each committed Advanced edit (via ThemeBuilderWindow forwarding LayoutChanged to ApplyLayoutNow). In the Advanced tab, ApplyField ends by calling LoadSelectedLayerIntoFields, whose RaiseGuides raises LayoutChanged.
- The Games List is a Grid host (GamesListHost) holding the TreeView. Shape layers, custom layers, Splash Image and Video Preview borders are applied by ApplyShapeLayers, ApplyCustomLayers, and ApplyBorder (3.8).
- **ApplyLayout repaints only when a style value changed.** It builds key strings from the entries and compares them with the last ones: `_lastGamesListStyleKey` (folder font/colors/shadow, selected-state shadow, arrow) triggers MainViewModel.RefreshFolderColorsLive; `_lastGameTitleStyleKey` (game title font/colors/shadow, selected-state shadow) triggers RefreshGameColorsLive; `_lastMarqueeLogoPath` (the Marquee entry's ImagePath) triggers MainViewModel.RefreshMarqueeLogo; `_lastSearchButtonsStyleKey` (every style field on the SearchLabel, SearchBox and RandomButton entries) triggers MainViewModel.RefreshSearchButtonBindings plus MainWindow.RefreshMainButtonsRestingColors; `_lastMainBackgroundKey` (the MainBackground entry's ImagePath and ImageDisabled) triggers MainViewModel.RefreshMainWallpaper plus RefreshMainBgVideo (the latter only once the window has loaded, 3.11); `_lastGameInfoStyleKey` (every Text*, TextShadow* and SectionHeader* field on the GameTitle, PublisherBlock, GameInfoBody, GameInfoNav and ImagePreviewsNav entries) triggers MainViewModel.RefreshGameInfoBindings (3.12); `_lastSplashPath` (the SplashImage entry's ImagePath) triggers MainViewModel.RefreshBootSplash; `_lastVideoFallbackPath` (the VideoPreview entry's ImagePath) triggers MainViewModel.RefreshMissingPreview (3.8). The Video Preview background color needs no key: `VideoPreviewLayer.ApplyBackground` runs on every ApplyLayout next to ApplyBorder. **Any new style field must be added to the matching key (or get its own) or it will not repaint live.**

### 3.4 Theme Builder window: edit and save flow
- Advanced tab edits change Configuration.Layouts **in memory only**, applied live. Values commit on Enter or on losing focus; invalid input reverts to the stored value. The user likes this behavior and wants it on every new property.
- **Save Adjustments** (window button): writes settings.json (the Advanced and Global tabs already edit the settings live; the Basic tab holds no values, so there is no sync step since Pass 6), including the working layouts (a new size stays in the Resolution combo after reopening the builder or restarting the launcher) and the editor preferences such as `NewSizeScaleChoice`, commits a pending custom size, moves the close-restore point, refreshes theme bindings.
- **Save Changes** (Themes Manager row at the top of THEME BUILDER): writes the theme zip (theme.json plus bundled assets). Layouts, ActiveWidth and ActiveHeight are saved in theme.json. Every layout entry's ImagePath (shape, custom, Marquee logo, Random Game Display, Main Window Background wallpaper, Splash Image, Video Preview fallback) is bundled into the zip and rewritten to an archive-relative path; LoadTheme rewrites them back to extracted paths.
- **Global tab** edits (3.15) also apply live: they write straight into the flat ConfigurationSettings values and republish the Global resources, so Save Adjustments and Save Changes only persist them (the Basic tab holds no values; its old load and sync methods were removed in Pass 6).
- **Closing the window without saving** restores Layouts, the active resolution and the flat Global values (3.13) to the last saved snapshot, republishes the Global resources and reapplies the main window.
- **Reset Layer / Reset Layout** restore from SavedThemeLayouts (the theme as last loaded or saved) with registry defaults filling gaps. **Restore Defaults** ignores the theme and uses registry defaults. Reset Layer copies ImagePath back for every non-custom layer, so the Marquee logo and the Main Window Background wallpaper are covered.
- "Theme sizes" buttons list the sizes saved in the theme file (`SavedThemeLayouts`), so the row changes only after Save Changes. The Resolution combo lists presets plus any size with a working layout (a new size joins it on Apply or a preset pick; closing the builder without saving removes it again). A Theme sizes button for a size with no working layout (removed but not saved) shows the New size layout prompt (3.1).
- The main window's hamburger menu has Themes and Layout size submenus, and Theme Builder opens with Ctrl+T.
- Alignment guides: drawn on `GuideOverlay`, a full-window Canvas above LayoutCanvas in MainWindow.xaml, so every line runs to the window edge (also maximized or fullscreen; offset by LayoutCanvas' origin, redrawn on overlay SizeChanged). Two independent toggles: **Edge guides** (`ChkShowGuides`, ShowGuideLines; label was "Show guides") draws four 1px lines at the selected layer's edges (the bounding box in multi mode); **Center guides** (`ChkCenterGuides`, ShowCenterGuide, default off) draws a vertical and a horizontal line crossing at the center of the same rect the edge guides use (the selected layer, the group part last clicked into via `_guidePartId`, or the multi-mode bounding box), so it follows the layer as it moves or resizes. On layers with an outside border (`HasOutsideBorder`, decision 59) the guide rect is the ring's outer box (X, Y, W + 2B, H + 2B) from `GetGuideRect` (decision 62), single, multi-select and Center guides alike. The Marquee layer's guides stay on the Marquee rect: the no-art banner card's ring is centered inside it and is not framed. Both use GuideLineColorHex, set from the "Color:" swatch (`GuideColorPicker`) on the guides line. `GuideInfo` carries `ShowRect` / `ShowCenter`; RaiseGuides returns null (nothing drawn) with no single or multi selection, on Main Window Background, or with both toggles off, so center guides never show without a selection. Preferences are editor settings in settings.json (loaded in the MainViewModel constructor, saved with the whole settings object), not part of the theme.
  - **Background grid (2026-10-23, `background-grid.md`, decision 58):** a session-only editor aid; nothing is saved (not in settings.json, the theme, any layer entry or ConfigurationSettings). The guides line reads: Edge guides, Center guides, "Color:" with the swatch only (the guide color hex box `TxtGuideColorHex` and its LostFocus handler were removed 2026-10-23; the swatch's own popup still has a hex entry; `GuideColorPicker_ColorChanged` writes GuideLineColorHex, which is unchanged, and calls `RaiseGuides()`), then `ChkBgGrid` ("Grid", off on every builder open), `TxtGridSpacing` (no label, width 52, tooltip "Grid spacing (px)", default 20), then an "Offset:" label and two 52px boxes `TxtGridOffsetX` / `TxtGridOffsetY` (tooltips "Grid offset X (px)" / "Grid offset Y (px)"), each in a Grid with a muted overlaid placeholder `PhGridOffsetX` / `PhGridOffsetY` ("X" / "Y", font size 13, `ChromeTextMuted`, not hit-testable) shown whenever its box is empty, the same pattern as the main window's folder-name popup placeholder (`FolderNameInputPlaceholder`). Spacing takes any number greater than 0 (whole or decimal, no upper limit), is stored in the Advanced tab's `_gridSpacing` rounded to 2 decimals (`MidpointRounding.AwayFromZero`, matching `Fmt`, so the box and the grid agree), applies on Enter or focus loss, and invalid input (text, 0, negative, empty) reverts to the stored value. Offsets (`_gridOffsetX` / `_gridOffsetY`, session-only like the spacing, never saved) are in layout units from the window's top-left, the same origin as LayoutCanvas: empty means 0 (the grid starts at the top-left); any finite number is accepted (negative, larger than the spacing, decimals), stored rounded to 2 decimals (`MidpointRounding.AwayFromZero`; `ParseGridOffset`, which also turns -0 into 0); they apply on Enter or focus loss (`ApplyGridOffsets` reads both boxes), invalid input reverts to the stored value's display, and the redisplay (under `_loading`) shows a stored 0 as an empty box, so typing 0 or -0 clears the box back to its greyed letter. Placeholder visibility is set from code: `TxtGridOffset_TextChanged` and an explicit `RefreshGridOffsetPlaceholders()` after the redisplay, which skips a null placeholder while the controls are still being created. The grid still fills the whole window on both sides of the offset. The Advanced tab raises `GridChanged(on, spacing, offsetX, offsetY)` (`Action<bool, double, double, double>`) from `RaiseGrid()`; ThemeBuilderWindow forwards it to `MainWindow.SetBackgroundGrid(on && onBuilder, spacing, offsetX, offsetY)`. The signature is `SetBackgroundGrid(bool on, double spacing, double offsetX = 0, double offsetY = 0)`, so the `(false, 0)` calls stay valid; `UpdateBackgroundGrid` passes the stored offsets to `BackgroundGridLayer.SetGrid(spacing, offsetX, offsetY, color)`. Shown only while THEME BUILDER is the selected top-level tab: leaving the tab calls `SetBackgroundGrid(false, 0)` (the checkbox stays checked and the grid returns with the tab via `RaiseGrid()`), and so does the Closed handler. Layer, resolution and theme changes never turn it off or reset the spacing or offsets. While on, `UpdateBackgroundGrid` sets a local `RootLayoutGrid.Background` (a cached frozen solid brush of `ThemeMainColor`), which hides the wallpaper image like "Disable background image"; collapses `MainBgVideoHost` (not `MainBgVideo`, so `RefreshMainBgVideo` keeps owning the player; the video keeps decoding while hidden); and shows `BackgroundGridLayer` (MainWindow.xaml, right after `MainBgVideoHost` and below LayoutCanvas, not hit-testable, filling the root grid, so lines run from the window's top-left at fullscreen too). Off clears both local values. Line color (`GetBackgroundGridLineColor`): the background's RGB (alpha ignored), luminance `0.2126R + 0.7152G + 0.0722B`; under 128 it blends `BackgroundGridContrastOnDark` (0.18) toward white, otherwise `BackgroundGridContrastOnLight` (0.30) toward black; always opaque. It follows live color edits through `if (_backgroundGridOn) UpdateBackgroundGrid();` in ApplyLayout's `_lastMainBackgroundColor` block. Drawing (`Views/BackgroundGridLayer.cs`): per axis the offset is first reduced to `start = ((offset % spacing) + spacing) % spacing`, so huge or negative offsets never loop over millions of lines; every line sits on a whole physical pixel at `round((start + k * spacing) * scale) / scale` with half-pixels rounded up (`Math.Floor(x * scale + 0.5)`, never round-half-to-even, see section 7) and is `1 / scale` thick, with the scale from `VisualTreeHelper.GetDpi`. The loop in `BuildPositions` starts at k = -1 and keeps that line when it snaps to 0 or more: a start that lands just under the spacing through floating-point error would otherwise drop the line at 0; each line is its own `DrawRectangle` in OnRender (vertical full height, horizontal full width, one frozen opaque brush, aliased edges); the snapped positions are cached and rebuilt only on a size, spacing, offset or DPI change (`SetGrid` clears them when the spacing or either offset changes; `OnRenderSizeChanged`, `OnDpiChanged`), and a color change only swaps the brush. Below 2 screen pixels of spacing the layer fills solid with the line color. Fractional spacings make the line-to-line distance alternate by one pixel (12.5 at 100% with no offset: lines at 0, 13, 25, 38, so 12 and 13 px between line starts and 11 and 12 px of clear space between 1px lines).
- **Launcher comes to the front (2026-10-22):** `MainWindow.BringToFrontAfterChildClose` (Background-priority dispatch: restore if minimized, Activate, Focus; no Topmost) runs at the end of ThemeBuilderWindow's Closed handler and after ShowDialog returns for Options, Sorting (both openers), Manage Playlists and RomCopyPath, so the launcher no longer drops behind other programs. If Activate ever fails, the fallback is a brief Topmost on then off.
- **Theme Saved flash:** `BrdThemeSavedFlash` sits in ThemeBuilderWindow beside the tab headers on a fixed black `ChromeBg` / `ChromeBorder` with green text, so no theme color can clash with it.
- **Sub-windows fit the work area (2026-10-26):** `Services/WindowFit.KeepInWorkArea(window)`, called after InitializeComponent in ThemeBuilderWindow, OptionsWindow, SortingWindow, ManagePlayListsWindow and RomCopyPathWindow, caps MaxWidth / MaxHeight to the work area (the screen minus the taskbar) of the window's monitor (`MonitorBounds.TryGetPhysicalWorkArea`, divided by the window's DPI scale) on SourceInitialized, moves a normal window back inside the work area once it is loaded, and re-applies both on DpiChanged. Window sizes are DIPs, so on a 1080p screen the Theme Builder (885) was cut off at 125% and above, Options (700) at 150% and Sorting (610) at 175%. Their content row is star-sized with the buttons row Auto, and the tab pages scroll, so a shorter window keeps its buttons visible. The code-built name prompt (SizeToContent, about 150 tall) is not hooked.

### 3.13 Global resources (foundation built 2026-10-21, Global tab migration Pass 1)

### 3.17 Smart fullscreen (Pass 1 built 2026-10-26, smart-fullscreen-pass1.md)
- **What it does:** with the editor preference on, toggling fullscreen (F11 or the hamburger's Toggle Fullscreen) picks one of the theme's saved layout sizes and a whole-number scale n for the window's monitor in **physical pixels**, cancelling the Windows scale setting, so text and shapes re-render sharp and only raster art is stretched. When no size fills the screen at a whole number, a fractional fallback scale fills it instead (2026-10-28, below). With the preference off, fullscreen behaves exactly as before (decision 63).
- **Preference:** `ConfigurationSettings.SmartFullscreen` (bool, default false), an editor setting in settings.json like the guide toggles: loaded in the MainViewModel constructor next to `ShowGuideLines`, saved by `PersistConfigurationToDisk` (whole object). Not in ThemeSettings, LoadTheme, `ApplyThemeSettings`, the `BtnSaveTheme_Click` DTO or GlobalThemeResources. Hamburger item "Smart fullscreen" (`Tag="SmartFullscreenMenu"`, right under Toggle Fullscreen, `HamburgerSmartFullscreenMenuItem_Click`); its check mark is set in `PopulateHamburgerSubmenus` with `CreateCheckIcon()`. Turning it off while scaling drops to plain fullscreen at once; turning it on while in fullscreen runs the size test at once (Smart when it fits, as a manual Smart fullscreen, not auto-entered), otherwise it takes effect the next time fullscreen is entered (consistency pass, 3.19).
- **Size test (pure, `Services/SmartFullscreen.cs`):** `SmartFullscreen.Choose(screenWidthPx, screenHeightPx, dpiScale, layoutSizes)` returns `SmartFullscreenResult(Fits, LayoutWidth, LayoutHeight, Scale, Centered, TransformFactor)`. For each size n = floor(min(screenW / w, screenH / h)); n < 1 is skipped; the largest covered area (w*n by h*n) wins, a tie goes to the larger layout; `Centered` is true unless the covered area is the whole screen; `TransformFactor` = Scale / dpiScale. No fit: `Fits` false and fullscreen stays plain. Sizes come from `Configuration.SavedThemeLayouts` (the sizes in the theme zip, the same list as the Layout size submenu), distinct; **only the active size** while the Theme Builder is on screen (3.19 consistency pass), so a size with only a working layout is valid there.
- **Fractional fallback (2026-10-28):** `Choose(..., allowFractional = true)`; `SmartFullscreenResult.Scale` is a `double` and the record carries `FromFallback` (default false). The whole-number pass above runs first, unchanged; its pick is returned as is when it fills the screen (not `Centered`) or when `allowFractional` is false. Otherwise `ChooseFractional` runs over the same sizes: s = min(screenW / w, screenH / h), scale-up only (s < 1 is skipped, so the fallback never finds a fit the whole-number pass missed); the largest covered area by rounded whole-pixel areas (`round(w*s) * round(h*s)`, so equal ratios do not near-tie in doubles) wins, a tie goes to the larger layout (3200x1800: 1080 at 1.667 beats 720 at 2.5). **Seam snap:** sCover = max(screenW / w, screenH / h); when the overflow on both axes is at most 1 physical pixel (`SeamTolerancePx`), s becomes sCover and `Centered` is false, and the window clips the overflow (1366x768 with a 1280x720 layout: s = 1.0672, 1366 x 768.5, a quarter pixel cropped top and bottom instead of a dark sub-pixel column at each side). A layout genuinely short on an axis stays `Centered` (1360x768 from 720: s = 1.0625, 1.5px bars). `FromFallback` is true only when the fallback changed the size or the scale; otherwise the whole-number result is returned. Same magnifier (TransformFactor = s / dpiScale); no setting, no toggle, no UI. `ApplySmartFullscreen` passes `allowFractional: false` while the Theme Builder is on screen (3.19) and keeps the session-only `_smartFullscreenFromFallback` (set from the result, cleared by `EndSmartFullscreen`; nothing saved). Decode sizes, popup scale, check mark and recompute hooks need no change (they read the factor or the size, never assume a whole number); the background grid and guides only show with the builder open, so they never see a fallback factor. Size picks are unaffected: they stay gated by `IsExactFitForMonitor` (an exact fit fills at 1x, so the fallback never runs for it; any other pick in fullscreen still drops to windowed). Accepted trade-off: at a fractional factor (rounding off) 1px borders, menus, tooltips and raster art soften.
- **Monitor:** `Services/MonitorBounds.TryGetPhysicalSize(hwnd, out monitor, out width, out height)` (`MonitorFromWindow` nearest + `GetMonitorInfo` full bounds, not the work area). Physical pixels need the **Per-Monitor V2 manifest** (`app.manifest`, `<ApplicationManifest>` in the csproj; before it the app was System DPI aware and GetDpi always returned the primary monitor's scale). WinForms' Screen is not used.
- **Transform host (MainWindow `[SECTION: Smart Fullscreen]`, `ApplySmartFullscreen` / `EndSmartFullscreen`):** `RootLayoutGrid` gets a frozen `ScaleTransform(f, f)` as **LayoutTransform**, Width / Height = the picked layout size, centered (HorizontalAlignment / VerticalAlignment Center), a local `UseLayoutRounding=false`, and the Window gets a local black `Background`, so the wallpaper image, wallpaper video, background grid, LayoutCanvas and GuideOverlay all scale together and any leftover screen is black bars. LayoutCanvas keeps its logical size (ApplyLayout is unchanged). `EndSmartFullscreen` clears every one of these local values (ClearValue) and the display override; ToggleFullscreen's exit path calls it **before** SizeToContent comes back, so the windowed size is unchanged.
- **Display override (session-only, MainViewModel `[SECTION: Smart Fullscreen Display Layout]`):** `SetDisplayLayoutOverride((w, h)?)` sets or clears it and calls RefreshThemeBindings (which re-applies the main window layout); `DisplayLayoutWidth` / `DisplayLayoutHeight` are the override or the active resolution; `ResolveDisplayLayout()` resolves the working layout at that size, falling back for an override size to a **clone** of the theme's saved copy (`_displayLayoutThemeCopy`, made in SetDisplayLayoutOverride; ResolveLayout fills gaps in place, so SavedThemeLayouts is never handed to it). Readers: `GetLayerEntry` (every Theme* forwarder), `ApplyLayout`, `ApplyRandomGameDisplayRect()` (die click), `UpdatePreviewTargetSize`, `IsRandomDisplayBackgroundTranslucent`. It never reaches ActiveResolutionWidth / Height, Layouts, SavedThemeLayouts, the Theme Builder's close-revert snapshot or theme.json. The Layout size submenu's check mark shows the displayed size while scaling (3.19).
- **Decode sizes:** `_layoutScaleFactor` (f while scaling, else 1) multiplies the FFmpeg preview target size (`UpdatePreviewTargetSize`) and the flyer slot size (`SetFlyerSlotSize` in ApplyLayout), so the preview video and flyers decode at the physical size they are shown at.
- **Recompute (`RecomputeSmartFullscreen`, only while scaling):** Window `DpiChanged`, `SmartFullscreen_LocationChanged` (only when `MonitorFromWindow` returns a different monitor than `_smartFullscreenMonitor`), `SystemEvents.DisplaySettingsChanged` (unsubscribed on Closed), a theme switch (hamburger Themes submenu or the builder's Load Theme), a size pick (both with the rules in 3.19), and closing the Theme Builder (which reruns it whenever the preference is on and the window is fullscreen, so a plain fullscreen left by the builder comes back to Smart). A rerun that finds no fit, or cannot read the monitor, drops to plain fullscreen.
- **Theme Builder:** it edits the active resolution. As built in Pass 1, opening it always dropped to plain fullscreen and F11 with it open did plain fullscreen; Pass 3 kept Smart only while the smart layout was the active size and dropped to plain otherwise. **Since the consistency pass (3.19):** while it is on screen Smart fullscreen shows only the active size at that size's own best whole-number scale, never the fractional fallback (plain only if it cannot fit at 1x); opening it while another size is showing first makes the shown size the active size (in memory, 3.19), so nothing changes on screen, and closing it reruns the builder-closed size test.
- **Guides and previews:** GuideOverlay sits inside RootLayoutGrid, so the guides line up with no code change (`TranslatePoint` origin stays 0, `GuideInfo` stays in layout units); they draw n physical pixels thick and stop at the canvas edge (not the screen) when centered. The Random Game Display card preview and the banner preview are inside LayoutCanvas and simply scale. The background grid's lines are n px wide and its snapping (GetDpi only) may blur at fractional factors; it is an editor aid, and since the builder can now stay in Smart fullscreen (3.19) this can be seen at 125% and above.
- **Testing status:** the fractional fallback (2026-10-28) is checked by a scratch harness only (30 cases, the whole-number regressions included), not yet on screen; to test: a 720-only theme on 1080p (1.5x), 1600x900 and 1366x768 display modes (1.25x and the seam snap), menus and tooltips at 1.5x, the Theme Builder open / close jump. Verified on a 1080p monitor at Windows scales 100/125/150/175 (a 960x540 test theme at 2x; a 720-only theme centered; menus, popups, tooltips, the color picker dropdown, Theme Builder fit, auto-enter / auto-drop / restore / close, the Layout size check mark). **Not verified on hardware:** 1440p (720 at 2x), 4K (1080 at 2x, 720 at 3x), moving the window between monitors of different scale, Per-Monitor V2 across mixed-DPI monitors.
- **Not in Pass 1:** the main window's menus, popups and tooltips are separate windows and did not follow the scale (Pass 2, built: 3.18); auto fullscreen on a size pick, auto-drop to windowed (Pass 3, built: 3.19); a raster scaling mode setting (WPF default for now, decision 7 of the spec; the marquee images keep their existing `HighQuality`).

### 3.18 Smart fullscreen: menus and popups (Pass 2 built 2026-10-26)
- **Why:** menus, submenus, popups and tooltips are separate windows. They take the monitor's DPI and are anchored correctly (WPF maps the placement target through RootLayoutGrid's transform), but their content does not inherit the LayoutTransform, so in smart fullscreen they drew at the Windows scale. Now they draw at the **whole-number part of the canvas scale** (2026-10-28): m = max(1, floor(s + 1e-9)) / dpiScale (`SmartFullscreen.PopupFactor`), while the canvas keeps its exact factor f = s / dpiScale. With a whole-number s (every case before the fractional fallback, and always with the Theme Builder open) m = f, so nothing changed; with a fallback s (1.5, 1.25, 1.0672, 1.333) menus and popups stay at 1x physical while the canvas is magnified. Identical at every Windows scale (m cancels it, so at 125% and above they are smaller than windowed, as they already were at s = 1). Windowed mode, plain fullscreen and every sub-window are unchanged.
- **Carrier:** two **Window resources** in MainWindow.xaml (`[SECTION: Smart Fullscreen Popup Scale]`, at the top of Window.Resources): `Launcher.PopupScale` (default `ScaleTransform` 1, 1) and `Launcher.PopupLayoutRounding` (default `sys:Boolean` True; `xmlns:sys` added to MainWindow.xaml, same mapping as App.xaml). A third, **`Launcher.InheritedPopupScale`** (default `ScaleTransform` 1, 1, added 2026-10-28), is m / f for the two folder popups, which inherit the canvas factor f (below). `ApplySmartFullscreen` sets `PopupScale` to a frozen `ScaleTransform(m, m)` (no longer the canvas's own transform object), `InheritedPopupScale` to a frozen `ScaleTransform(m / f, m / f)` and rounding to false (keys `PopupScaleKey` / `InheritedPopupScaleKey` / `PopupLayoutRoundingKey`), and keeps m / f in the session-only `_inheritedPopupFactor`; `EndSmartFullscreen` puts back `Transform.Identity` (both scales), true, and 1. No other code writes them, so every start, recompute (DPI, monitor, display settings, theme switch, Layout size pick) and end (exit, Theme Builder drop, preference off, no fit) is covered, and windowed and plain fullscreen always end with factor 1 and rounding on. DynamicResource repaints an open menu when they change. Not in App.xaml, GlobalThemeResources, MainViewModel or anything saved; sub-windows resolve their own resources and cannot see them.
- **Readers (root element of each popup window, LayoutTransform plus UseLayoutRounding):** the implicit `ContextMenu` style (every Games List menu: folder, game, empty space, and the hamburger, and through it every submenu, see below); the four main button tooltips, set in code by `DelayedTooltipTimer_Tick` when it opens them (see the tooltip fix below; the implicit ToolTip style first added for them never reached them and was removed); the `FolderNameInputPopup` and `FolderColorPickerPopup` Borders (rounding, plus `LayoutTransform="{DynamicResource Launcher.InheritedPopupScale}"` since 2026-10-28: they inherit f and the compensation m / f brings them to m); the color picker's swatch and its own dropdown by inheritance (m, through the folder-color popup's Border; see the fix below; the picker's local Grid style, BasedOn the untouched `PickerPopupGridStyle`, only sets rounding on `Name = MainGrid`); and the code-built ROM copy tooltip (`ShowRomCopyStatusTooltip`), which sets both values from `FindResource` directly.
- **Submenus inherit the scale (fix 2026-10-26):** a WPF Popup that sits in a visual tree copies its ancestors' accumulated transform (scale and rotation, not translation) onto its own popup root. The MenuItem template's `SubmenuPopup` is inside the parent menu, so it already gets the ContextMenu's scale, and for a deeper level the parent submenu's popup root, which carries that same scale. The first build also put `Launcher.PopupScale` on the SubmenuPopup Border, so every submenu drew at f squared (about 4x at 100% with n = 2) and a submenu of a submenu would have been f cubed. The Border now has no LayoutTransform, so each level is scaled exactly once; it keeps `UseLayoutRounding="{DynamicResource Launcher.PopupLayoutRounding}"` explicitly so rounding stays off while scaled. A top-level ContextMenu and the tooltips are different: their Popup has no visual parent (it is placed only by PlacementTarget or the mouse), so nothing is inherited and they set the scale themselves. The two folder popups and the color picker's dropdown are declared inside the scaled tree and inherit, like a submenu (fix below).
- **Folder popups and color picker at double scale (fix 2026-10-26, two steps):** `FolderNameInputPopup` and `FolderColorPickerPopup` are declared inside `RootLayoutGrid` (Window > RootLayoutGrid > Popup), so like a submenu each Popup copies its ancestors' combined transform, including RootLayoutGrid's LayoutTransform of f, onto its own root. The Pass 2 audit wrongly listed them as having no scaled tree around them. With `Launcher.PopupScale` also on their Borders they drew at f squared (swatch about 104px and wheel about 750px at 100% with n = 2, against about 26 and 190 windowed). The first fix attempt removed the scale from the picker's local `Name = MainGrid` trigger on the theory that MainGrid was the swatch's top Grid; that was wrong (the swatch did not change, so MainGrid belongs to the dropdown only, StandardColorPicker), though the removal was still right, since the dropdown inherits too. The real fix removed `LayoutTransform` from both popup Borders, which keep only `UseLayoutRounding`; the MainGrid trigger keeps only rounding. Now the folder-name popup, the folder-color popup, the swatch and the picker dropdown (whose Popup sits in the folder-color popup's tree) each get f exactly once, by inheritance. **Since 2026-10-28** their Borders also read `Launcher.InheritedPopupScale` (m / f), a compensation, not a second scale: f times m / f = m, the menus' scale, and the picker's dropdown inherits that m (f times m / f) through the Border. It is 1 whenever s is a whole number (windowed, plain fullscreen, the Theme Builder open, s = 2 or 3), and below 1 only for a fractional fallback (m / f = 0.667 at s = 1.5). The dropdown fit (`FitFolderColorDropdown` / `GrowFolderColorDropdown`) measures pixels per layout unit with `PointToScreen` on every open, so it follows m with no change.
- **Button tooltips at 1x (fix 2026-10-26):** the four main button tooltips (Random, Sorting, Options, Menu) are `<Border.ToolTip>` property values with `ToolTipService.IsEnabled="False"`, opened by hand (`MainButton_MouseEnter` > `DelayedTooltip_MouseEnter` > `DelayedTooltipTimer_Tick` sets `IsOpen`). ToolTipService never attaches them to their owner, so they are in no logical tree: the implicit ToolTip style in MainWindow.Resources never applied (they used App and theme defaults), and their popup has no visual parent, so nothing is inherited. `DelayedTooltipTimer_Tick` now sets `LayoutTransform` and `UseLayoutRounding` from `FindResource(PopupScaleKey / PopupLayoutRoundingKey)` right before opening (the ROM copy tooltip pattern), so they draw at f once while scaled and at 1x otherwise (the value is read at each open). The unused implicit ToolTip style was removed.
- **Color picker dropdown placement (final, 2026-10-26):** the dropdown is PortableColorPicker's internal Popup (`popup`, StaysOpen False, default Placement Bottom of the swatch). Left to WPF it opened below the swatch and, in smart fullscreen (about 760px tall at 2x), ran past the bottom of the screen. MainWindow `[SECTION: Folder Color Picker Dropdown Fit]`: `HookFolderColorDropdown` (once, from `FolderColorPickerControl.Loaded`) finds it with `FindName("popup")` (fallback: the first Popup in the picker's visual tree) and handles Opened and Closed. `FitFolderColorDropdown` pass 1, after layout on every open, measures in physical pixels with `PointToScreen`: the folder-color popup's Border (`FolderColorPickerPopup.Child`), the dropdown's top-left and its pixels per layout unit (transforms and DPI included), and its true height from `MeasureUnclampedHeight` (the content measured with an infinite constraint plus the Border's thickness and padding; ActualHeight is clamped to the room left on screen). Placement is one rule: **right** of the popup (8px gap, tops aligned) if it fits inside the work area's right edge, else **left** (right edge 8px left of the popup) if that fits inside the left edge, else **below the swatch** where WPF put it; then, if its bottom is past the work area bottom, up by exactly the overflow, never above the work area top. The move is `HorizontalOffset = moveX / scaleX` and `VerticalOffset = moveY / scaleY`. Pass 2 measures the real movement per axis and corrects each offset in proportion, then `GrowFolderColorDropdown` re-measures the content and the popup root (the window was sized against the space below the ORIGINAL position) and, if the content is still short, sets an explicit Height of the desired height. Closed resets both offsets and clears a forced height. The same rule runs in windowed mode, plain and smart fullscreen, at any Windows scale, for high and low rows; no scale is set on the dropdown.
- **Layout rounding is off while scaled** for the same reason as the canvas (3.17): WPF rounds to device pixels ignoring the transform, so at 125% / 150% / 175% rounding would put whole layout units on fractional pixels.
- **Placement:** anchors are unchanged (hamburger under its button, row menus at the mouse, submenus to the right of their item, the rename and color flyouts and the ROM tooltip under the row). Create folder's MousePoint offsets are -20 / -18 times `_inheritedPopupFactor` (m / f, 2026-10-28): the folder-name Popup sits inside RootLayoutGrid, so WPF applies the inherited f to its offsets, and m / f makes them follow the content, which draws at m (1 whenever s is a whole number, so the offsets are the plain -20 / -18 then; the `* _layoutScaleFactor` added in the first build was removed with the folder popups fix). Rename (Bottom, 0 / 0) is unchanged. WPF keeps popups on the monitor, so larger menus flip left or up sooner near an edge instead of clipping.

### 3.19 Smart fullscreen: auto fullscreen and the Theme Builder refinement (Pass 3 built 2026-10-26)
- **Scope:** only with the Smart fullscreen preference on; with it off, everything behaves as before. Startup never goes fullscreen. Nothing reaches theme.json. Writes to settings.json happen only through `SwitchActiveLayoutSize` with `persist` true (a hamburger Layout size pick, and the entry-size restore when fullscreen is left with F11 or the menu item) and `PersistFullscreenEntrySizeOnClose` (closing in a fullscreen with an entry size); the Theme Builder open's adopt calls `SwitchActiveLayoutSize(..., persist: false)` and writes the active size in memory only. All of them may copy a layout from SavedThemeLayouts into Layouts when it is missing, as the pick always did.
- **One enter path, one exit path (MainWindow `[SECTION: Fullscreen Toggle]`):** `EnterFullscreen(bool smart)` (window style, maximize, then `ApplySmartFullscreen` when asked) and `ExitFullscreen()` (`EndSmartFullscreen` first, then the normal window with `SizeToContent`). `ToggleFullscreen` (F11 and the menu item) clears the auto-entered flag and the entry size and calls one of them; `EnterFullscreen` then remembers the active size as the entry size (after the size test, 2026-10-27). `IsFullscreen` is `WindowStyle == None`.
- **Size picks (consistency pass, 2026-10-26):** the hamburger Layout size pick (`HamburgerLayoutSizeItem_Click`) and the Theme Builder's Theme sizes buttons and size combo (through `SizePickRunner`) all run through **`MainWindow.RunSizePick(doSwitch)`**, then `HandleLayoutSizePickForFullscreen`. **Every pick writes the active size, in every state** (the old manual-Smart early return is gone, so leaving an F11-entered fullscreen stays at the picked size). The hamburger's already-active return applies only when nothing would change (same active size and no Smart fullscreen showing another size); picking the active size while Smart fullscreen shows another one is a pick (the fullscreen pick rule below). Only a windowed pick can auto-enter; startup, a theme switch while windowed, and the builder's custom size Apply, Remove / Delete Size and Load Theme never auto-enter.
- **Exact 1x fit:** `SmartFullscreen.IsExactFit(screenWidthPx, screenHeightPx, width, height)` (pure) against `MonitorBounds.TryGetPhysicalSize` for the window's nearest monitor (`IsExactFitForMonitor`), so the Windows scale does not matter (1920x1080 on a 1080p monitor fits at 100% and at 150%; 1280x720 does not; on 1440p or 4K these sizes never fit). For an exact-fit size `Choose` returns that same size at n = 1, so the auto-entered screen shows exactly the picked layout.
- **`HandleLayoutSizePickForFullscreen`:** preference off: nothing. Windowed + exact fit: `EnterFullscreen(true)` and set the flag (if the size test did not apply, it exits again, so no auto-entered plain fullscreen is left); windowed + no exact fit: stays windowed. **Any fullscreen** (auto-entered, Smart entered with F11, or plain): an exact fit reruns the size test (`ApplySmartFullscreen`, which picks that size), so a plain fullscreen becomes Smart and is never a dead end; anything else **drops to windowed** (`ExitFullscreen()`) at the newly picked size, with no re-centering, like F11's exit (user decision 2026-10-26, replacing the consistency pass's pinned-size rule, which showed e.g. 1280 x 720 at 1x with black bars on 1080p); the drop clears the entry size. A pick that stays fullscreen keeps the entry size (2026-10-27), so F11 out still returns to the size active when fullscreen was entered. Works the same with the Theme Builder open or closed.
- **Auto-entered flag `_smartFullscreenAutoEntered`** (session-only, false at startup): set only after a successful auto-enter. Cleared by every manual toggle (`ToggleFullscreen`) and by `EndSmartFullscreen` from any cause (exit, auto-drop, preference off, no fit, monitor read failure), so a plain fullscreen left behind is never auto-dropped. A recompute that stays smart (DPI, monitor move, display change, a Theme Builder size change) keeps it.
- **Entry size, restored on exit and saved on close (2026-10-26, extended to every fullscreen 2026-10-27, smart-fullscreen-entry-size.md):** the session-only `_fullscreenEntrySize` (was `_sizeBeforeAutoEnter`) is the active size when fullscreen was entered. **Set** by `EnterFullscreen` after its size test (F11 and Toggle Fullscreen, Smart or plain), overwritten by a successful auto-enter with the size from before its Layout size pick (the pick handler passes it in, read before `SwitchActiveLayoutSize` writes the new size), and by the Theme Builder open's adopt when none is remembered. **Kept** by a size pick that stays fullscreen (exact fit) and by every recompute that stays Smart. **Cleared** with no restore by every manual toggle (read first), a theme switch (`HandleThemeSwitchForFullscreen`), and `EndSmartFullscreen` from any cause (exit, auto-drop of a pick, preference off, no fit, monitor read failure); so it is always null while windowed. **F11 out:** `ToggleFullscreen` reads and clears it before `ExitFullscreen`, then `RestoreFullscreenEntrySize`: if the theme still has a layout at that size (Layouts or SavedThemeLayouts) and it is not already active, `SwitchActiveLayoutSize` writes the active size, re-applies the layout, saves settings.json and refreshes the Theme Builder (`RefreshAfterExternalSizeSwitch`), and the window sizes to it. This holds whatever changed the active size while fullscreen (an exact-fit pick, the builder's adopt, Save Adjustments keeping a builder pick), so F11 out never leaves a monitor-sized window taller than the work area. **App close:** on the real close (the second `MainWindow_Closing`, after the preview player has shut down) `PersistFullscreenEntrySizeOnClose` writes the entry size as the active size and saves settings.json, only while fullscreen with an entry size other than the active size and only if the theme still has that size (its layout is copied from SavedThemeLayouts when the working layouts lack it), so the next launch opens windowed at it. No ApplyLayout and no window change, since the window is closing. Nothing reaches theme.json.
- **Layout size check mark and manual smart fullscreen picks (2026-10-26):** `PopulateHamburgerSubmenus` puts the Layout size check on the layout on screen: while Smart fullscreen is scaling, the displayed size (`DisplayLayoutWidth/Height`), otherwise the active size; also the active size when the displayed one is not in the list. Display only, nothing is written. Since the consistency pass a pick writes the active size in every state, and in any fullscreen a pick that is not an exact fit drops to windowed, so the check follows the pick; a pick that stays fullscreen keeps the entry size, so F11 out returns to the size active at entry (the entry-size rule above), not to the picked size. An auto-entered fullscreen keeps the pick rules (auto-drop to the picked size, stay on an exact fit). The submenu is rebuilt on every open; a recompute while it is open (a DPI or display change) leaves its check stale until it is reopened. The Theme Builder's Theme sizes highlight stays on the active size.
- **Theme switch (`RunThemeSwitch`, `HandleThemeSwitchForFullscreen`):** LoadTheme sets the active size to the new theme's saved size. `MainWindow.RunThemeSwitch(doLoad)` sets `_deferBuilderDrop` around the load, the settings save and the refresh, so the Theme Builder check in ApplyLayout waits, then runs `HandleThemeSwitchForFullscreen` if it loaded. Used by `HamburgerThemeItem_Click` and, since 2026-10-27, by the builder's Load Theme (`ThemesManagerControl.ThemeLoadRunner`, set by ThemeBuilderWindow like `SizePickRunner`), so both follow the same rules. Auto-entered and that size is not an exact fit: auto-drop to windowed at that size. Otherwise, in fullscreen with the preference on, the size test reruns, so a plain fullscreen becomes Smart when it fits (not auto-entered). It never enters fullscreen from a window.
- **Theme Builder refinement (consistency pass):** while the builder is on screen the size test's only candidate is the active size (the one being edited), so Smart fullscreen always shows it (`SmartLayoutMatchesActiveSize` holds) at its own best whole-number scale (`allowFractional: false`, 2026-10-28), and ResolveDisplayLayout reads the working layout at that size, so live edits show; a size with only a working layout (an unsaved preset or custom size) is valid. Plain only when it cannot fit at 1x. `ApplySmartFullscreen` no longer refuses and drops to plain. **Opening the builder (2026-10-27):** when Smart fullscreen is showing another size than the active one (an F11 entry picks the best saved size), `OpenThemeBuilderWindow`, **before** the builder window is created, makes the shown size the active size with `SwitchActiveLayoutSize(..., persist: false)` (in memory only; Save Adjustments / Save Changes write it) and remembers the replaced size as the entry size when none is set (`??=`), so nothing changes on screen and F11 out returns to the old size. Right after creating the builder it sets the builder's **size restore point** to that pre-adopt size (`ThemeBuilderWindow.SetSizeRestorePoint`; the constructor had already taken the adopted size), so closing without saving puts the old size back as the active size; Save Adjustments, Save Changes, Load Theme and an outside size switch (`RefreshAfterExternalSizeSwitch`) still move it to the current active size. The layouts restore point is unchanged (the constructor's clone). Not through `RunSizePick`, which drops non-exact fits (1080 at 2x on 4K) to windowed. The old rerun after `Show()` is gone; since the fractional fallback (2026-10-28) `OpenThemeBuilderWindow` reruns `ApplySmartFullscreen` right after `Show()` only when `_smartFullscreenFromFallback` is set (the size already matches, so the ApplyLayout check would not fire), so the builder opens at the whole-number scale (an accepted visible jump, e.g. a 720 layout from 1.5x to a centered 1x on 1080p) and the close rerun brings the fallback back. The **check at the top of `ApplyLayout`** (smart active, `_themeBuilderWindow?.IsVisible == true`, a mismatch, and not `_deferBuilderDrop`) now reruns `ApplySmartFullscreen` instead of ending Smart fullscreen; it is still needed for active-size changes outside a size pick or theme switch (custom size Apply, Remove / Delete Size). ApplySmartFullscreen sets a new override or ends Smart, both refresh the bindings and rerun ApplyLayout, so the check returns. **Closing the builder:** its own Closed handler restores the snapshot size and calls ApplyLayoutNow while hidden (the IsVisible gate skips the check); MainWindow's later Closed handler clears `_themeBuilderWindow`; if the restore changed the active size (compared with the size captured in the builder's `Closing`) it clears `_smartFullscreenAutoEntered` (the picked size is gone; the entry size stays, so F11 out still returns to it); then, with the preference on and the window fullscreen, it reruns `ApplySmartFullscreen`, so Smart fullscreen goes back to the best saved size, also from a plain fullscreen left by a builder size the monitor cannot fit. After an adopt: closing while Smart still shows the adopted size restores the old active size behind it (the display stays, F11 out lands windowed at that size); closing after a builder pick dropped to windowed at the old size stays there; closing after Save Adjustments keeps the saved size active (F11 out still returns to the entry size).
- **`RunSizePick(doSwitch)` (consistency pass; was `RunBuilderSizePick`):** reads the previous active size, sets `_deferBuilderDrop = true`, runs the switch in try/finally (clearing the flag), then calls `HandleLayoutSizePickForFullscreen(newWidth, newHeight, previousSize)` unless nothing changed (same active size and no Smart fullscreen showing another size). The builder's Theme sizes buttons (`BtnSavedSize_Click`) and the size combo (`CboResolution_SelectionChanged`, which wraps `CboResolutionApply` only when a different `ResolutionPreset` is picked) reach it through `AdvancedThemesTabControl.SizePickRunner` (set by ThemeBuilderWindow; null or no MainWindow owner runs the switch directly); the hamburger pick calls it with `SwitchActiveLayoutSize`. The builder's switches stay in memory (no settings.json write; Save Adjustments does that); the hamburger's write settings.json as before. Custom size Apply and Remove / Delete Size are not size picks (they reach the ApplyLayout check); Load Theme goes through `RunThemeSwitch`. ### 3.20 Preview video playback (FFmpeg player; failure restart built 2026-10-28)
- **Players.** The game-preview video is the only video on the FFmpeg player (`Playback/*.cs`, DLLs in `4rcade5tick_files/ffmpeg`): `PreviewPlayerHost` > `VideoPresenter` > `VideoSession` (one decode thread per source, BGRA frames through a 4-frame queue) and, only when audio is requested, `AudioSession` + `WasapiOutput`. Frames are presented on the UI thread in `CompositionTarget.Rendering`. The boot splash video, the Main Window Background video, the shape / custom layer videos and the Random Game Display video use WPF `MediaElement` (muted) and are not covered here.
- **No audio at all ("muted" means no audio session).** `PreviewPlayerHost.Play(path, withAudio = false)`; MainWindow's `StartActivePreview` never passes audio on. With audio off `VideoSession.Decode` does not even look for the audio stream (`HasAudio` false), opens no `AudioSession` and no WASAPI endpoint, and the presenter's stopwatch clocks the video (the path files without an audio stream always used). `RestartAsync` / `SeekAsync` keep the choice. The audio path (WASAPI 200 ms buffer, audio master clock, underrun fails the session, `AudioSettings.Muted` gain) is unchanged and kept for the later sound feature (attract mode); nothing turns it on yet. Before 2026-10-28 a "muted" preview still decoded audio and wrote silent buffers to WASAPI as the master clock, so any stall of the audio thread over about 200 ms (idle, background, paging, GC, resume from sleep) threw "Audio buffer underrun" and ended the preview.
- **Stopwatch rebase.** On the stopwatch path nothing drops late frames, and while composition is stopped (minimized window) the stopwatch runs on but the decoder waits on the full queue. `VideoPresenter.RenderCore` rebases the clock onto the next frame when that frame is more than 0.5 s behind, so a restored window resumes where it froze instead of fast-forwarding the backlog. Applies to every stopwatch-clocked file.
- **Failure restart (MainWindow `[SECTION: Preview Auto-Restart]`).** `PreviewPlayerHost.StateChanged` forwards the presenter's `PlayerStateChanged` (state, source path, error text; superseded requests are already filtered by the presenter's request version). On Error for the source MainWindow asked for (`_previewSourcePath`, full path, compared case-insensitively) it logs, then restarts it from the start after 500 ms (`PreviewPlayerHost.Restart` → `RestartAsync`), at most 3 restarts per source. The count resets on every `StartActivePreview` (selection, return from a game, spin) and every stop (`StopMediaElementPreview`, which also cancels a pending restart), and when the attempt had reached Playing 30 s or more before the next error. No restart (checked at the error and again when the timer fires) while auto-restart is off (`SetPreviewAutoRestart(false)`, public, for attract mode), while a game runs (`_gameBeingLaunched`), while the Options window is open (its Pause), or while the Video Preview layer or surface is hidden. After the limit the slot stays on the layer's background color, as before.
- **Failure log.** `4rcade5tick_files/logs/preview.log` (folder created on first failure; the app had no logs folder before), one line per Error: timestamp, error text, source path, `attempt` (restarts already made for that source; 0 is the original play), window `active`/`inactive` and `WindowState`, and `retry=yes (restart n of 3)` or `retry=no (reason)`. Written on the UI thread only on failure; write errors go to Debug output.
- **Not covered:** an error while the Options window is open is logged with no restart, and Resume on close does nothing on a failed session, so that preview stays stopped until the next selection.

## 4. Design decisions (settled)

1. **Layer by layer**, Games List first (it carried font family, shadows and other styling), then reuse what works for the next layers.
2. **Backgrounds and borders are flat "shape layers"** placed under any layer. Content layers get only X, Y, Width, Height, Z-order and visibility. **No margins** on content layers. Anything inside a row's geometry stays hard-coded for now. (Built; the Basic tab's Marquee and Games List panel background, border and corner-radius fields were removed 2026-10-18.)
3. **No legacy-theme migration.** Nobody is using older themes; the schema may break freely, and the user's own themes can be deleted and rebuilt. Older saved entries are filled from registry defaults when read; a theme saved with a flat logo or panel colors simply falls back to the built-in logo and defaults.
4. **Live apply on Enter or focus change** for every Advanced property, the same as placement works now.
5. **Fonts:** a dropdown of 11 Windows core fonts, no bundled fonts. List: Segoe UI, Arial, Bahnschrift, Georgia, Times New Roman, Palatino Linotype, Impact, Arial Black, Segoe UI Black, Consolas, Courier New. Segoe UI is the fallback. Impact, Arial Black and Segoe UI Black are already heavy, so Bold makes little difference on them.
6. Layer **grouping or linking** (a panel moving with its backdrop) is a later QoL item, after all layer properties exist.

## 7. Traps and gotchas

- ConfigurationSettings has no change notification; layer values reach XAML through MainViewModel Theme* forwarders, and RefreshThemeBindings must raise every one. Flat Global values never get a forwarder; they are Global resources (decision 50).
- A new flat theme property must be wired into all of these or it silently reverts: ThemeSettings DTO, ConfigurationSettings, ApplyThemeSettings (also the settings.json load in the MainViewModel constructor), LoadTheme mapping, the DTO builder in BtnSaveTheme_Click, `GlobalThemeResources` (key, Apply, snapshot, the App.xaml default) and a Global tab field (3.15). The Basic tab's old load and sync methods are gone (Pass 6). Storing values on layer entries avoids most of these but adds the entry-field traps below.
- Styling values go on LayerLayoutEntry. A new field must be added to `CopyStyleFrom` (which CloneLayouts, the resolution-switch copy and Reset Layer all use), to the registry's default building and ResolveLayout fill-ins, and to the matching style key in ApplyLayout (3.3), or it will not survive copies or repaint live.
- **Main window buttons:** their Background, BorderBrush and icon Foreground are set from code (hover and resting), which replaces the XAML BorderBrush binding. Each button is two layers: the outer Border holds the fill, the inner Border ring holds the border color and the icon (3.10). Any new button style value must be applied to the correct layer in both `MainButton_MouseEnter` and `ApplyMainButtonRestingColors`. Do not confuse the MainWinBtn forwarders with the Global Buttons values (BtnBgColorHex, OptionsBtn*), which only reach `ThemedActionButtonStyle`.
- Do not use ancestor-walk (RelativeSource AncestorType) bindings in row templates for values; push them from MainViewModel onto TreeCategoryNode and GameItem. The only ancestor lookups left in the row templates are the IsSelected and IsMouseOver triggers.
- The folder and game row templates each have their own "selected row" trigger; they look alike; keep them in their own template.
- The shadow effects are built once per refresh and frozen; every row shares the same object. Do not mutate them after building.
- A new color for a static (non-custom) folder follows the Recently/Most Played/Favorites pattern: a ...ColorFile property, ReadFolderColorFile, IsCustomColor = true, a Set...Color method, a branch in FolderColorPickerPopup_Closed, and canRecolor in FolderRowContextMenu_Opened.
- **Never test the top-level tab by index.** The alignment guides (3.4) must show only while THEME BUILDER is the selected tab. ThemeBuilderWindow.xaml.cs checks `ReferenceEquals((ThemeBuilderTabControl.SelectedItem as System.Windows.Controls.TabItem)?.Content, ThemeBuilderPage)` in both places (the `AdvancedTab.GuidesChanged` forwarder and the tab `SelectionChanged` handler). Both once tested `SelectedIndex == 1`; when the tabs were reordered (THEME BUILDER moved to index 0) the guides silently vanished from the builder and showed on the Theme Browser tab instead. Any new code that depends on which top-level tab is showing must compare the tab's `Content` to the tab's direct content (`ThemeBuilderPage`, `ThemeBrowserTab`, `GlobalTab`). Since 2026-10-22 `AdvancedTab` sits inside `ThemeBuilderPage`, so comparing to `AdvancedTab` is always false and hides the guides.
- **Background grid drawing (3.4):** `BackgroundGridLayer` draws one `DrawRectangle` per line in OnRender. Never go back to one combined geometry (GeometryGroup, PathGeometry union, a single StreamGeometry or frozen shape): on screen in the hardware renderer the combined version dropped diagonal wedges of lines and lagged badly at spacings of 10 and below, though offscreen software renders were perfect. A tiled `DrawingBrush` is also out: it drops or blurs lines whenever spacing times scale is not a whole number of pixels (125% and 150%, fractional spacings).
- **Background grid gating:** the grid is deliberately not in `StopPreviews` (that runs on every layer change, resolution switch and theme load, which must not turn the grid off). It follows the guides' tab gating in ThemeBuilderWindow (the `GridChanged` forwarder and the SelectionChanged handler), comparing the tab `Content` to `ThemeBuilderPage`, never an index.
- **Background grid local values:** do not set `RootLayoutGrid.Background` or `MainBgVideoHost.Visibility` anywhere else. The grid owns those local values while on (`UpdateBackgroundGrid`) and clears them with `ClearValue` when off, which hands the background back to the root grid's Style and the video host back to its default.
- **Background grid rounding:** `BackgroundGridLayer` rounds snapped positions half-up (`Math.Floor(x * scale + 0.5) / scale`), never with `Math.Round`'s default round-half-to-even. At spacing 5 with offset 2.5 the default rounding put lines at 2, 8, 12, 18 (gaps alternating 4 and 6 px) instead of 3, 8, 13, 18.
- **Background grid offset placeholders:** `PhGridOffsetX` / `PhGridOffsetY` are driven from code (`TxtGridOffset_TextChanged` plus an explicit `RefreshGridOffsetPlaceholders()` after the redisplay in `ApplyGridOffsets`), not DataTriggers, and the refresh must skip a null placeholder while the controls are still being created.
- Closing the Theme Builder reverts layouts and the flat Global values (3.13) to the last saved snapshot. Anything else stored outside layouts is not covered unless handled separately. A new Global property must be added to `GlobalThemeResources` (key constant, `Apply`, `CaptureSnapshot`, `RestoreSnapshot` in its area) and to the App.xaml default block, besides the usual flat-property wiring.
- **Chrome Palette styles are keyed and hex-free (3.14):** a new fixed color goes into `[SECTION: Chrome Palette]` as a named brush, never as a hex value inside a style. Do not add an implicit (keyless) style to App.xaml; it would restyle the main window's search box, TreeView or menus. Styles in App.xaml that reference `ArcadeDarkScrollViewer` or a palette key with `StaticResource` must come after it in the file. A style moved into App.xaml keeps working only if its bindings do not depend on the UserControl it left (the shared Theme Builder, tab and button styles hold no bindings any more, only Global and palette resources).
- **Action buttons:** do not set Background, Foreground, BorderBrush or BorderThickness on a `ThemedActionButtonStyle` button (in XAML or code). A local value overrides the style and the button stops following the Global Buttons values. The only intended exception is the Advanced tab's active saved-size button (`Global.Button.BgHover` by `SetResourceReference`).
- **Line endings:** `.cs` and `.xaml` files are CRLF; `.md` files (this one included) are LF, enforced since 2026-10-23 by `.gitattributes` (`*.md text eol=lf`; CLAUDE.md says the same). Keep each file's own endings when editing.
- **A Global value lives in one editor, the Global tab.** Do not add theme value fields to the Themes Manager or THEME BROWSER (the Basic tab no longer exists; it had no load or sync step since Pass 6; a second editor would overwrite the live value on save). The save DTO line in `BtnSaveTheme_Click` is required (it reads the settings). Readers use `{DynamicResource Global...}` (or `SetResourceReference` in code), never a binding to the property, which would not repaint live (3.15).
- **Global resources are typed:** a `{DynamicResource Global...}` target gets the resource object as is, with no conversion. Font sizes must be published as `double` (not the `int` setting), border sizes as `Thickness`, radii as `CornerRadius`, colors as `Brush`; a wrong type fails silently at runtime.
- LoadTheme deletes and re-extracts the theme's Extracted folder; ThemeExtractionStarting releases open files first.
- Saved files still contain a stale VideoConvertPrompt layer from the removed video converter. It is ignored on load and drops out on the next save.
- Games List cannot be hidden (the registry forces it visible).
- Visual Studio can keep stale generated XAML files after large edits; clean and rebuild.
- Do not reopen: the single-MediaElement background video loop (a two-player swap was tried and rejected).
- **Advanced tab:** every control x:Name and handler is referenced from code-behind; a whole-file XAML replacement must keep them all. `LoadSelectedLayerIntoFields` starts with `ApplyLayerTabs(...)`, which only returns to the Position tab when the selected layer id changes. The shadow Color/Blur/Depth controls are enabled through `IsEnabled` bound to their toggle's `IsChecked`.
- **Marquee:** MarqueeImage is also null while a background decode runs after a game is selected, so the banner must use MarqueeMissing, never HasMarqueeImage. Anything that sets MarqueeImage to null for "nothing selected" must also clear MarqueeMissing. Code reading the marquee must not assume MarqueeImage always has a value.
- **Marquee banner:** the no-art card is a ControlTemplate (`MarqueeBannerCardTemplate`), so its elements bind the view model forwarders directly (they inherit the window's DataContext) and read the title through `RelativeSource TemplatedParent`; a DataTemplate would lose the DataContext. The banner Text* fields share the MarqueePanel entry with the shared image shadow (TextShadow*), so the GI table's `Marquee` block must stay ShadowOnly or its size and font writers would edit the banner. The banner preview sets local Visibility on `NoMarqueeBanner`, `MarqueeLogoImage` and `MarqueeDisplay`; anything else that sets them locally must clear them the same way.
- **Border ring rule (decisions 57, 59 and 62).** On Video Preview, Splash Image, Shape Layers 01 to 04, custom layers and both Random Game Display states, Width / Height are the content size, the border is drawn outside it, and X / Y are the ring's outer top-left corner (content at X + B, Y + B). The no-art banner card has no rect of its own: its ring is centered inside the Marquee rect and the Marquee guides stay on the Marquee rect. Code that needs the content area reads the entry (W / H, origin X + B, Y + B), never the control's Canvas size or position; the guides use the outer box (`GetGuideRect`, `LayerRegistry.HasOutsideBorder`). Place a new bordered layer with `PlaceOutsideBorder` / `ApplyRingBox`; do not copy the arithmetic. Do not move this into the shared positioning loop. Exempt: the Search & Buttons row. WPF puts a Border's CornerRadius on the stroke centerline, so test corners at radius 20 / border 3 and radius 2 / border 6.
- The Splash Image, Video Preview and Game Info layer controls bind only Theme* properties that still exist; none used the removed panel properties (checked 2026-10-18).
- **Game Info tabs:** the shared GI handlers find controls by name (`GI{Block}{Control}`, block key in Tag). A renamed or missing control is a runtime failure, not a build error. A new Game Info style field also needs a line in `_lastGameInfoStyleKey`, `FillGameInfoStyle` and (for header fields) `GIStyle` (3.12).
- **Media loading version counter and cache key (MainViewModel, Instant Media Loading):** every SelectedGame change increments `_mediaSelectionVersion`; background decodes check it before each file read and again in the UI callback, and drop stale results. Anything that starts a background load for the *current* game without a new selection (ResolveMarqueeImage, SetFlyerSlotSize) must pass the current version, not increment it, or the game's other pending loads are discarded. Background code must only use the `ImageRequest` it was given (path, key, flyer slot size snapshotted on the UI thread), never view model state. The decoded-image cache key is full path + last-write time + length (+ slot size for flyers); a new art source must use `MakeImageRequest` so replaced files and size changes decode fresh. Only successful decodes are cached; "file missing" is always re-checked. `LoadBitmapFromFile` and `LoadFlyerBitmap` are static for this reason.
- **Random Game Display message:** an empty `TextMessage` is a saved choice (no text), so fill it with `??=` and never with `IsNullOrWhiteSpace`, or an empty message silently comes back as "Rolling the Dice!". The per-state max size, wrapped width and file clip are set in code (`ApplyRandomGameDisplayCardSize`), not through forwarders, because they depend on which state's rect is active (3.16). Background and border are per state: read them from the active state's part (the forwarders through `RandomDisplaySplashState`, the clip and wrapped width from `stateEntry`), never from RandomGameDisplay alone, or the splash state silently takes the game-selected look. Code that picks the active state must use `RandomDisplayFromSplash` (preview state while the card preview is on), not `_randomSpinFromSplash` directly.
- **GI block gating:** each GI block is gated on its own `SelectUnit` row, not on "Game Info selected". The `Marquee` block (Marquee layer's Shadow tab) lives in the GI table but is only active while the Marquee layer is selected; `LoadMarqueeShadowFields()` is called from LoadSelectedLayerIntoFields next to the Marquee logo branch. A new block for another layer must set `SelectUnit`, or its tab will never load or save.

- **Smart fullscreen (3.17):** code that needs the layout the main window is showing reads `MainViewModel.ResolveDisplayLayout()` / `DisplayLayoutWidth` / `DisplayLayoutHeight`, never `ActiveResolutionWidth` / `Height` with `Layouts` directly, or it shows the wrong size's values in smart fullscreen; code that edits, saves or snapshots keeps using the active resolution. Never write the override into ActiveResolution*, Layouts, SavedThemeLayouts or a snapshot, and never hand `SavedThemeLayouts` itself to ResolveLayout (it fills gaps in place; clone first). Anything that sets a local value on `RootLayoutGrid` (LayoutTransform, Width, Height, alignment, UseLayoutRounding) or the Window's Background must be cleared in `EndSmartFullscreen`, and the exit path must clear them before SizeToContent comes back. Decode sizes from `GetDpi` must also multiply by `_layoutScaleFactor`. `DpiChanged` and physical monitor sizes need the Per-Monitor V2 `app.manifest`; do not remove it or switch to a DPI-unaware manifest.

- **Smart fullscreen popups (3.18):** a new main window menu, popup or tooltip must have its root element read `{DynamicResource Launcher.PopupScale}` and `{DynamicResource Launcher.PopupLayoutRounding}` (the ContextMenu and SubmenuPopup styles cover ordinary menus; a Popup's child needs it set itself, and any ToolTip opened by hand (`IsOpen = true` with ToolTipService off, or built in code) gets it in code at open time). Set the scale only on a popup that does not inherit one: a Popup placed inside an already scaled tree (a submenu, or any Popup inside a scaled menu or popup) copies its ancestors' scale onto its root, so adding `Launcher.PopupScale` to its child scales it twice (the SubmenuPopup bug, 3.18). Check where the Popup element is declared, not where it opens: a Popup declared anywhere under `RootLayoutGrid` (the folder-name and folder-color popups, and anything inside them such as the color picker's dropdown) inherits RootLayoutGrid's LayoutTransform f and must not get `Launcher.PopupScale` (that would be f times m). **Compensation exception (2026-10-28):** such a Popup's child reads `Launcher.InheritedPopupScale` (m / f) so it lands on the menus' scale m; this is the only scale allowed on an inheriting popup, and only on the Popup's direct child (the two folder popup Borders), never on anything inside it (the picker's dropdown inherits m from the Border). Only popups with no visual parent set it themselves: a ContextMenu's popup, a ToolTip (set in code at open time for the four button tooltips and the ROM copy tooltip: a ToolTip held only as an element's `ToolTip` property value and opened by hand is not in the window's tree, so a window implicit style or DynamicResource never reaches it). Offsets on an inheriting Popup are scaled by the inherited f (WPF applies it to them), so never multiply them by `_layoutScaleFactor`. **Offset exception (2026-10-28):** an inheriting popup with the compensation multiplies a fixed offset by `_inheritedPopupFactor` (m / f) so it follows its m-scaled content (Create folder's -20 / -18); only a non-inheriting popup with a MousePoint offset would need it multiplied by m (none exists today). Do not scale an element by its Name inside a third-party control. Only `ApplySmartFullscreen` / `EndSmartFullscreen` write the three resources and `_inheritedPopupFactor`; setting `InheritedPopupScale` without the canvas scaled would shrink the folder popups. Never add the scale to `PickerPopupGridStyle` or App.xaml (the Theme Builder shares them) or to the Global resources.

- **Smart fullscreen auto-entered flag (3.19):** `_smartFullscreenAutoEntered` must be cleared by `EndSmartFullscreen` from every cause (it is cleared first, before the not-active early return) and by every manual toggle; set it only after a successful auto-enter. If a cause skipped it, a plain fullscreen left by a failed size test could later be auto-dropped to windowed, and a fullscreen the user chose would be undone.
- **Fullscreen entry size (3.19):** `_fullscreenEntrySize` is separate from `_smartFullscreenAutoEntered` on purpose: `ToggleFullscreen` clears the flag first, so the exit restore must read the entry size on its own (and read it before `ExitFullscreen`, whose `EndSmartFullscreen` clears it). Set it in `EnterFullscreen` **after** the size test (its no-fit path clears it). A size pick that stays fullscreen must keep it; clear it with no restore on a theme switch and in `EndSmartFullscreen` (every cause). Restore only a size the theme still has (Layouts or SavedThemeLayouts), through `SwitchActiveLayoutSize`, never by writing ActiveResolution directly. The Theme Builder open's adopt must run before the builder window exists and must not save settings.json.
- **Layout size menu in Smart fullscreen (3.19):** the check mark is display-only (the displayed size while scaling) and must never feed a write. Every pick goes through `RunSizePick` and writes the active size; the already-active return applies only when nothing would change (same active size and Smart fullscreen not showing another size), or a click on the active size while another one is displayed would do nothing.
- **Visible-Builder gate in ApplyLayout (3.19):** the Theme Builder check at the top of `ApplyLayout` requires `_themeBuilderWindow?.IsVisible == true`, not just a non-null window. The builder's Closed handler restores its snapshot size and calls `ApplyLayoutNow` while `_themeBuilderWindow` is still set (MainWindow clears it in a later Closed handler, which then reruns the size test); a non-null gate would rerun the size test with the builder rule during the close. The check reruns `ApplySmartFullscreen` (never ends Smart fullscreen directly) and keeps its `return`; `_deferBuilderDrop` must be set around every size pick (`RunSizePick`) and the hamburger theme switch, so their handlers decide once.
- **Smart fullscreen fractional fallback (3.17, 3.19):** the fallback never applies while the Theme Builder is on screen (`ApplySmartFullscreen` passes `allowFractional: false`), and opening the builder reruns the size test after `Show()` when `_smartFullscreenFromFallback` is set; keep that rerun, since the ApplyLayout check only fires on a size mismatch. Size picks stay gated by `IsExactFitForMonitor`: a pick in fullscreen that is not an exact fit still drops to windowed and never uses the fallback. Keep comparing fallback areas as rounded whole pixels (equal ratios near-tie in doubles) and keep the seam snap, or a 1366x768 screen shows a dark sub-pixel column at each side.
- **Re-entrant ApplyLayout (3.19):** when that check calls `EndSmartFullscreen`, End clears the display override and refreshes the theme bindings, which runs `ApplyLayout` again in full from inside the outer call. The outer call must `return` right after, or it would finish a second pass with values it read before the drop. Keep the check first in ApplyLayout, before anything is resolved.

- **New size scaler (3.1, decision 65):** the prompt opens before `RunSizePick`, never inside it, so Cancel never reaches `_deferBuilderDrop` or `HandleLayoutSizePickForFullscreen`. The combo path opens it through `Dispatcher.BeginInvoke` after putting the combo back (a modal dialog over an open dropdown is avoided); keep that. `LayoutScaler.Scale` runs only on the fresh copy, after the background resize; never hand it `_currentLayout`, `SavedThemeLayouts` or a layout that already exists. A new nullable font or border size field on `LayerLayoutEntry` must be added to `LayoutScaler.ScaleStyleSizes` (with its range) or A leaves it unscaled. A value measured inside a scaled box (like the banner's reference-box text size) must stay out. The mismatch test is `LayoutScaler.FactorsDiffer`, shared by the prompt's warning line and the Search & Buttons rule (`IsPositionOnlyOnMismatch`); do not add a second one. Media layers stretch per axis on purpose (final decision 65); do not bring back a keep-your-ratio rule without the user. The one exception is the Video Preview (`LayerRegistry.IsUniformSizeOnMismatch`, Width and Height by u on a mismatch, decided 2026-10-28); do not extend it to other layers, and keep it behind that helper and the same `FactorsDiffer` test. Apply commits the custom size; do not bring back a second commit step. Rounding is half away from zero, never `Math.Round`'s default.

- **Sub-window sizes (3.4):** a new sub-window calls `ArcadeStick.Services.WindowFit.KeepInWorkArea(this)` after InitializeComponent, keeps its content in a star-sized row with the buttons row Auto, and lets tall content scroll; its fixed Width / Height are DIPs and grow with the Windows scale. Do not set MaxHeight / MaxWidth on these windows elsewhere (WindowFit owns them).

- **Folder-color picker dropdown fit (3.18):** the dropdown is a third-party internal Popup (`popup` inside PortableColorPicker), reached by name, so WPF's own flip and screen constraint cannot be trusted for it; recheck the `popup` name and the `FindName` lookup if the ColorPicker package is updated (if both fail, the hook silently does nothing). Never measure it with `ActualHeight`: WPF clamps an open popup's content to the room left on screen, so `ActualHeight` always looked like it fit; the true height is the unclamped `DesiredSize` (infinite constraint), and the scale comes from `PointToScreen`. A moved popup must be re-measured: its window is sized against the space below its ORIGINAL position, and changing an offset moves the window without re-measuring it, so without `GrowFolderColorDropdown` the content stays cropped at its old height. Placement is always right of the folder-color popup, then left, then below the swatch, then up by any overflow; keep it after-the-fact (measure after open, offsets set from measured scales, a second pass checking the real movement) and reset both offsets (and any forced height) on close so nothing accumulates. Never set a scale on the dropdown (it inherits one).
